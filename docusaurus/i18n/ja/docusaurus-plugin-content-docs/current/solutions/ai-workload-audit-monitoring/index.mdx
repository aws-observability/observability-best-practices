# AWS における AI ワークロードのモニタリングと監査

## 概要

AWS 上の最新の AI ワークロードは、3 つの独立したパイプラインにわたってテレメトリを生成します — CloudTrail（誰が何を呼び出したか）、Bedrock モデル呼び出しログ（モデルが何と言ったか）、そして ADOT SDK によって収集されるエージェントテレメトリ（エージェントがどのように動作したか）。各パイプラインは不可欠です。CloudTrail 単体では、IAM ロールが `InvokeModel` を呼び出したことは分かりますが、そのロールがモデルに何を尋ねたか、エージェントがどのように応答したかは分かりません。モデル呼び出しログはコンテンツをキャプチャしますが、エージェントのオーケストレーションは記録しません。ADOT はオーケストレーションをキャプチャしますが、推論パラメータや IAM アイデンティティは記録しません。セキュリティおよびオペレーション調査では、ほぼ常に少なくとも 2 つのパイプラインの相関が必要です。

このガイドでは、以下の方法で AI ワークロードの完全なモニタリングと監査ストーリーを構築する方法を説明します：

1. **3 つのテレメトリパイプラインすべてを有効化** — このガイドでの簡単なセットアップに加え、詳細については関連ガイドへのディープリンクを提供します。
2. **CloudTrail 上に検出ルールを構築** — Bedrock および AgentCore データイベントの両方をカバーする、セキュリティと監査サーフェス向けのメトリクスフィルター、アラーム、および Contributor Insights ルール。
3. **パイプライン横断の相関クエリを実行** — CloudTrail と Bedrock モデル呼び出しログおよび ADOT スパンを結合して、単一のパイプラインでは回答できない質問に答えます。

[生成 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/generative-ai-scoping-matrix/)および[エージェント型 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)は、AI アプリケーションを構築する際に組織が対処する必要があるセキュリティディメンションを定義しています。これには、監査とログ、アイデンティティコンテキスト、エージェンシー境界、データ保護が含まれます。このガイドは、CloudTrail、CloudWatch、およびパイプライン横断の相関を使用して、それらのディメンションの具体的な実装を提供します。以下のタブは、各マトリックスディメンションをそれを実装するガイドセクションにマッピングしています。

### 3 つの複合的な課題

**ボリューム** — AI モデルの呼び出しは大量のイベントを生成する可能性があります。正確なイベントセレクターと集約がなければ、大量のイベントの中から関心のあるイベントを分離するのは困難であり、すべてをキャプチャするコストは高額になります。

**スピード** — エージェントが開始するアクティビティシーケンスは、数秒以内に複数の API コール、ツール呼び出し、モデルインタラクションを伴う場合があります。ニアリアルタイムの検出ルールは、運用上の異常をより早い段階で表面化させ、より迅速なトリアージと調査開始時間の短縮を支援します。

**複雑さ** — AI ワークロードのアクティビティは複数の AWS サービスにまたがります。単一のログソースでは完全な可視性は得られません。パイプライン間の相関が、調査が実際に行われる場所です。

### このガイドでカバーする内容

- 3 つのテレメトリパイプラインと各パイプラインが一意にキャプチャする内容
- 3 つすべての有効化（CloudTrail を詳細に、他の 2 つは簡単な手順とディープリンクを提供）
- CloudTrail 固有の検出：Bedrock および AgentCore データイベントの両方に対するメトリクスフィルター、アラーム、Contributor Insights
- AgentCore データイベント：ゲートウェイトラフィック、ビルトインツールの使用、認証情報アクセス、メモリオペレーション、ランタイムアクティビティ
- 調査のためのパイプライン横断の相関クエリ
- 3 つのデータソースすべてを組み合わせた統合ダッシュボード

## 使用するタイミング

- Amazon Bedrock、Amazon Bedrock AgentCore、またはセルフホストモデルを使用して AWS 上で AI ワークロードを構築、運用、またはセキュリティ保護している場合
- AI モデルの呼び出し、エージェントのアクション、ツールの使用に対する完全な監査証跡を確立する必要がある場合
- 生成 AI セキュリティスコーピングマトリックスまたはエージェント型 AI セキュリティスコーピングマトリックスで定義されたセキュリティディメンションを実装している場合
- CloudTrail、Bedrock モデル呼び出しログ、エージェントテレメトリ（ADOT SDK）間でアイデンティティ、コンテンツ、パフォーマンスデータを相関させる必要がある場合
- 不正アクセス、ガードレールの変更、ログの中断、またはエージェント認証情報アクセスの異常をニアリアルタイムで検出したい場合
- AI ワークロード向けに CloudWatch メトリクスフィルター、アラーム、Contributor Insights ルール、またはパイプライン横断の相関クエリを設定している場合
- AI ワークロード向けにセキュリティ監査、オペレーションモニタリング、コスト配分を組み合わせた統合 CloudWatch ダッシュボードが必要な場合

## ガイダンス

### 生成 AI テレメトリランドスケープ：3 つの補完的なパイプライン {#the-genai-telemetry-landscape-three-complementary-pipelines}

CloudTrail は、AWS 上の AI ワークロードに対して完全なオブザーバビリティを提供する 3 つのテレメトリパイプラインの 1 つです。各パイプラインは異なるデータをキャプチャし、異なる目的に使用され、異なる方法で有効化されます。セキュリティ調査では、ほぼ常に少なくとも 2 つのパイプラインの相関が必要です。

![3 つの生成 AI テレメトリパイプライン](/img/cloudops/recipes/AWS%20CloudTrail/monitoring-and-auditing-genAI/pipelines.png)

| パイプライン | キャプチャ対象 | ロググループ | 主な用途 |
| --- | --- | --- | --- |
| **CloudTrail** | 誰が何をしたか — すべての API コール、呼び出し元 ARN、ソース IP、エラーコード、アクセス拒否、コントロールプレーンの変更 | `YOUR_CLOUDTRAIL_LOG_GROUP` | セキュリティ監査、アクセス調査、設定変更の追跡 |
| **Bedrock モデル呼び出しログ** | モデルが何と言ったか — 完全なプロンプト、完全なレスポンス、推論パラメータ（temperature、max_tokens）、呼び出し元 IAM アイデンティティ、トークン数 | `bedrock-model-invocation-logging` | コンテンツ監査、コンプライアンス、プロンプト品質デバッグ、コスト配分 |
| **エージェントテレメトリ（AWS Distro for OpenTelemetry — ADOT によって収集）** | エージェントがどのように動作したか — モデルコールのレイテンシ、ツール実行、分散トレース相関、セッション追跡 | `aws/spans`、`/aws/bedrock-agentcore/runtimes/<agent>` | オペレーションモニタリング、パフォーマンスデバッグ、エージェントワークフローオブザーバビリティ |

#### 各パイプラインが単独で回答できる質問

**CloudTrail 単独で分かること：**

- どの IAM アイデンティティが `InvokeModel` を呼び出したか？
- ソース IP、ユーザーエージェント、リージョンは何か？
- コールは拒否されたか（AccessDenied、UnauthorizedOperation）？
- 誰かがガードレールを変更したか、ログを停止したか、IAM 権限をエスカレーションしたか？
- どの VPC エンドポイントがコールをブロックしたか？

**モデル呼び出しログ単独で分かること：**

- モデルに送信されたプロンプトは何か？
- モデルは何を返したか？
- どの temperature と max_tokens が使用されたか？
- コールはいくつの入力トークンと出力トークンを消費したか？
- レスポンスは切り捨てられたか（stop_reason = max_tokens）？

**エージェントテレメトリ（ADOT SDK）単独で分かること：**

- モデルコールにかかった時間（クライアント側のレイテンシ）は？
- エージェントはどのツールをどの順序で呼び出したか？
- ツールが失敗した場合、どのコンポーネントがエラーの原因か？
- エージェントセッションは複数のモデルコールにわたってどのようにチェーンされているか？

#### 相関が調査を可能にする場面

**相関でのみ回答できる質問**

| 調査の質問 | 結合するパイプライン | 結合キー |
|---|---|---|
| 誰がモデルにこの質問をし、モデルは何と答えたか？ | CloudTrail（呼び出し元）+ モデル呼び出しログ（プロンプト/レスポンス） | requestId |
| エージェントの障害はモデルの問題か、ツールの問題か、権限の問題か？ | ADOT スパン（コンポーネントのレイテンシ/エラー）+ CloudTrail（AccessDenied イベント） | session + time |
| これらの安全でないモデルレスポンスの直前にガードレールが弱体化されたか？ | CloudTrail（UpdateGuardrail イベント）+ モデル呼び出しログ（レスポンスコンテンツ） | timestamp |
| エージェントロールは最小権限に違反する Bedrock コールを行っているか？ | CloudTrail（引き受けたロールからのクロスサービス AccessDenied）+ ADOT（エージェントセッション ID） | session + time |
| どの外部呼び出し元がゲートウェイを通じてこのエージェントをトリガーし、エージェントはどの認証情報を使用したか？ | CloudTrail ゲートウェイデータイベント（JWT サブジェクト、ソース IP）+ CloudTrail 認証情報データイベント（TokenVault/OAuth2 アクセス） | time + エージェントランタイム ARN |
| エージェントは意図されたスコープ外でコードを実行したりウェブサイトを閲覧したりしているか？ | CloudTrail AgentCore ツールデータイベント（CodeInterpreter/Browser）+ ADOT スパン（エージェントセッションコンテキスト） | session + time |

[パイプライン横断の相関クエリ](#cross-pipeline-correlation-queries)セクションで、これらのシナリオの実際の JOIN クエリを提供します。
:::

### 実装の概要 {#implementation-overview}

3 つのパイプラインすべてを有効化し、その上に検出と相関を重ねていくフェーズドロールアウトです。

#### フェーズ 1：オブザーバビリティパイプラインの有効化 {#phase-1-enable-observability-pipelines}

2 つのオブザーバビリティパイプライン（Bedrock モデル呼び出しログと ADOT SDK によって収集されるエージェントテレメトリ）から始めます。有効化は簡単で、相関クエリを可能にするものです。CloudTrail のセットアップはフェーズ 2 で行います。

**パイプライン A：Bedrock モデル呼び出しログ**

すべての Bedrock モデルコールについて、完全なプロンプト、レスポンス、推論パラメータ、呼び出し元 IAM アイデンティティをキャプチャします。手動でのオプトインのみです。*（データ主権要件とコンプライアンス監査ワークフローをサポートするためにモデルインタラクションをキャプチャすることで、[生成 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/generative-ai-scoping-matrix/)のガバナンスとコンプライアンスディメンションを実装します。）*

1. [Amazon Bedrock コンソール](https://console.aws.amazon.com/bedrock/)を開きます
2. **設定** → **モデル呼び出しログ** を選択します
3. ログを有効にし、送信先として CloudWatch Logs（および/または S3）を選択します
4. ロググループ名（デフォルト：`bedrock-model-invocation-logging`）とサービスロールを設定します

詳細な設定、PII マスキング、ダッシュボードのセットアップについては、[AWS における生成 AI オブザーバビリティ](../genai-observability/)を参照してください。

**パイプライン B：エージェントテレメトリ（ADOT SDK によって収集）**

エージェントのオーケストレーション、分散トレース、ツール実行をキャプチャします。

- **AgentCore：** ADOT SDK がランタイムにデフォルトで含まれており、テレメトリが `aws/spans` および `/aws/bedrock-agentcore/runtimes/<agent>` に自動的に流れるため、アクションは不要です
- **EKS/ECS/セルフホスト：** ADOT 自動計装エージェントをワークロードにアタッチします。コード変更は不要です

完全な Application Signals エクスペリエンスを有効にするには、[CloudWatch Transaction Search](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Enable-TransactionSearch.html) を有効にします。

詳細な有効化手順については、[AWS における生成 AI オブザーバビリティ — エージェント型ワークロードのオブザーバビリティの有効化](../genai-observability/)および [AgentCore オブザーバビリティクイックスタート](https://aws.github.io/bedrock-agentcore-starter-toolkit/user-guide/observability/quickstart.html#getting-started-with-agentcore-observability)を参照してください。

#### フェーズ 2：CloudTrail の有効化 — Bedrock から開始し、カバレッジを拡大し、CloudWatch に取り込む

AI ワークロードの監査サーフェス全体をキャプチャするように CloudTrail を設定します。最も価値の高いリソース（Bedrock）から始めて外側に拡大します。パイプライン A および B と結合できるよう、すべてを CloudWatch Logs に配信します。

**ステップ 1：Bedrock および AgentCore データイベントと管理イベント**

アドバンストイベントセレクターを使用して、トレイルで **Bedrock データイベント**を有効にします。これらのオペレーションはデフォルトではログに記録されません。[Amazon Bedrock データイベント](#amazon-bedrock-data-events)を参照してください。

:::note[有効にする Bedrock リソースタイプ]

| カテゴリ | リソースタイプ |
|---|---|
| エージェントとオーケストレーション | `AWS::Bedrock::AgentAlias`、`AWS::Bedrock::InlineAgent`、`AWS::Bedrock::FlowAlias`、`AWS::Bedrock::FlowExecution`、`AWS::Bedrock::Session` |
| モデル呼び出し | `AWS::Bedrock::Model`、`AWS::Bedrock::AsyncInvoke`、`AWS::Bedrock::PromptVersion`、`AWS::Bedrock::AdvancedOptimizePromptJob` |
| セーフティとガードレール | `AWS::Bedrock::Guardrail`、`AWS::Bedrock::AutomatedReasoningPolicy`、`AWS::Bedrock::AutomatedReasoningPolicyVersion` |
| ナレッジと RAG | `AWS::Bedrock::KnowledgeBase`、`AWS::Bedrock::Tool` |
| データオートメーション | `AWS::Bedrock::DataAutomationProject`、`AWS::Bedrock::DataAutomationInvocation`、`AWS::Bedrock::DataAutomationProfile`、`AWS::Bedrock::Blueprint` |

:::

アドバンストイベントセレクターを使用して **AgentCore データイベント**を有効にします。[Amazon Bedrock AgentCore データイベント](#amazon-bedrock-agentcore-data-events)を参照してください。

:::note[有効にする AgentCore リソースタイプ]

| カテゴリ | リソースタイプ |
|---|---|
| ランタイムとゲートウェイ | `AWS::BedrockAgentCore::Gateway`、`AWS::BedrockAgentCore::Runtime`、`AWS::BedrockAgentCore::RuntimeEndpoint` |
| ビルトインツール | `AWS::BedrockAgentCore::CodeInterpreter`、`AWS::BedrockAgentCore::Browser` |
| アイデンティティと認証情報 | `AWS::BedrockAgentCore::WorkloadIdentity`、`AWS::BedrockAgentCore::TokenVault`、`AWS::BedrockAgentCore::OAuth2CredentialProvider`、`AWS::BedrockAgentCore::APIKeyCredentialProvider` |
| メモリと評価 | `AWS::BedrockAgentCore::Memory`、`AWS::BedrockAgentCore::Evaluator` |

上記に加え、利用可能になった AgentCore リソースタイプもすべて有効にします。

:::

すべてのリージョンで**管理イベント**（読み取りと書き込み）が有効になっていることを確認します — これにより `InvokeModel` と `Converse` が管理イベントとして自動的にキャプチャされ、`CreateGateway`、`CreateGatewayTarget` などの AgentCore 管理イベントもキャプチャされます。[CloudTrail 管理イベント](#cloudtrail-management-events)を参照してください。

**CloudTrail Insights**（`ApiCallRateInsight` および `ApiErrorRateInsight`）を有効にして異常検出を行います。[CloudTrail Insights イベント](#cloudtrail-insights-events)を参照してください。

**ステップ 2：S3、Lambda、ネットワークアクティビティへの拡張**

- トレーニングデータ、モデルアーティファクト、CI/CD パイプラインバケット向けに Amazon S3 データイベント（書き込みのみ）を有効にします。[Amazon S3 および Lambda データイベント](#amazon-s3-and-lambda-data-events)を参照してください。
- 本番 AI パイプライン関数向けに Lambda データイベントを有効にし、開発/テストを除外します。[Amazon S3 および Lambda データイベント](#amazon-s3-and-lambda-data-events)を参照してください。
- Bedrock、S3、Lambda VPC エンドポイント向けにネットワークアクティビティイベントを有効にし、`VpceAccessDenied` をターゲットにします。[CloudTrail ネットワークアクティビティイベント](#cloudtrail-network-activity-events)を参照してください。

**ステップ 3：CloudWatch Logs への配信**

- CloudTrail トレイルを [CloudWatch Logs ロググループ](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/send-cloudtrail-events-to-cloudwatch-logs.html)に配信するよう設定します。

#### フェーズ 3：CloudTrail 上に検出ルールを構築

- CloudTrail イベント用のメトリクスフィルターを作成します（不正な Bedrock アクセス、ガードレールの変更、ログの中断）。[メトリクスフィルター](#metric-filters)を参照してください。
- 各メトリクスフィルターに SNS 通知ターゲット付きの CloudWatch アラームを作成します。[CloudWatch アラーム](#cloudwatch-alarms)を参照してください。
- トップ IAM アイデンティティとソース IP を特定するための Contributor Insights ルールを作成します。[Contributor Insights ルール](#contributor-insights-rules)を参照してください。

#### フェーズ 4：パイプライン横断の相関クエリを構築

- 標準的な CloudTrail 検出用の CloudWatch Logs Insights クエリを開発します。[セキュリティ分析](#security-analytics)を参照してください。
- CloudTrail と Bedrock モデル呼び出しログおよび ADOT スパンを組み合わせたパイプライン横断の JOIN クエリを構築します。[パイプライン横断の相関クエリ](#cross-pipeline-correlation-queries)を参照してください。
- 検証済みのクエリをセキュリティおよびオペレーションアナリストの繰り返し使用のために保存します。

#### フェーズ 5：イベント集約による最適化

- CloudTrail イベント集約（`API_ACTIVITY`、`RESOURCE_ACCESS`、`USER_ACTIONS` テンプレート）を有効にして、生のデータイベントと並行して 5 分間のサマリーを取得します。[CloudTrail データイベント集約](#cloudtrail-data-event-aggregation)を参照してください。
- CloudWatch サブスクリプションフィルターを使用して、管理イベントと集約イベントのみをダウンストリーム SIEM に転送し、取り込みボリュームを削減します。

#### フェーズ 6：統合ダッシュボードの構築

- CloudTrail アラーム、Contributor Insights ウィジェット、モデル呼び出しログのコストウィジェット、ADOT パフォーマンスウィジェット、相関クエリ結果を単一のペインに組み合わせた CloudWatch ダッシュボードを構築します。[統合監査・モニタリングダッシュボード](#unified-audit--monitoring-dashboard)を参照してください。

### Amazon Bedrock データイベント {#amazon-bedrock-data-events}

デフォルトでは、CloudTrail はアカウントの[管理イベント](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-management-events-with-cloudtrail.html)をログに記録します。これにより、`InvokeModel`、`Converse`、`ConverseStream` などの一般的な Bedrock ランタイムコールがすでにキャプチャされます。多くの主要な AI ワークロードオペレーションはデータイベントとしてログに記録されます。これには、エージェントの呼び出し、ナレッジベースの取得、フロー実行、ガードレールの適用、双方向ストリーミング、非同期呼び出し、プロンプトレンダリングが含まれます。これらのオペレーションには、トレイルでのアドバンストイベントセレクターが必要です。データイベントにより、セキュリティチームはモデル呼び出しの可視性を得ることができます。適用する具体的なセレクターについては、以下の[Bedrock 用のアドバンストイベントセレクター](#advanced-event-selectors-for-bedrock)を参照してください。

#### Bedrock 用のアドバンストイベントセレクター {#advanced-event-selectors-for-bedrock}

CloudTrail トレイルで Bedrock データイベントをキャプチャするには、以下のアドバンストイベントセレクターを使用します。各 Bedrock リソースタイプには独自のセレクターが必要であり、各セレクターは `resources.ARN` プレフィックスを使用してログをお客様の特定のリソースにスコープする必要があります。これにより、リソースタイプごとに 1 つずつ、18 個の個別のセレクターが設定されます。ほとんどのセレクターは `eventCategory = Data` でフィルタリングし、`resources.ARN` プレフィックスをアカウントにスコープします。`Model` と `AsyncInvoke` セレクターは、基盤モデルの ARN が AWS 所有でアカウント ID を含まないため、代わりに `eventName` フィルタリングを使用します。

:::warning
以下のセレクターは**サンプル**です。プレースホルダーを置き換えずに適用すると、イベントはキャプチャされません。
:::

:::note[Bedrock プレースホルダーリファレンス]

| プレースホルダー | 置き換え先 | 確認場所 |
|---|---|---|
| `ACCOUNT_ID` | 12 桁の AWS アカウント ID | AWS コンソール右上メニュー |
| `REGION` | AWS リージョン（例：`us-east-1`） | コンソールのリージョンセレクター |
| `AGENT_ID` / `ALIAS_ID` | エージェント ID とエイリアス ID | Bedrock コンソール → **エージェント** |
| `KB_ID` | ナレッジベース ID | Bedrock コンソール → **ナレッジベース** |
| `FLOW_ID` | フロー ID | Bedrock コンソール → **プロンプトフロー** |
| `GUARDRAIL_ID` | ガードレール ID | Bedrock コンソール → **ガードレール** |
| `PROMPT_ID` | プロンプト ID | Bedrock コンソール → **プロンプト管理** |
| `POLICY_ID` | 自動推論ポリシー ID | Bedrock コンソール → **自動推論** |
| `PROJECT_ID` | データオートメーションプロジェクト ID | Bedrock コンソール → **データオートメーション** |
| `TOOL_ID` | Bedrock ツール ID | Bedrock コンソール → **ツール** |
| `BEDROCK_EXECUTION_ROLE_NAME` | Bedrock コール用の IAM ロール名 | IAM コンソール → **ロール** |
| `YOUR_CLOUDTRAIL_LOG_GROUP` | CloudTrail トレイルの CloudWatch Logs ロググループ | CloudTrail コンソール → トレイル → **CloudWatch Logs** |

特定のタイプの**すべて**のリソースをログに記録するには、ARN プレフィックスからリソース ID を削除します（例：`agent-alias/AGENT_ID/ALIAS_ID` → `agent-alias/`）— これによりイベントボリュームとコストが増加します。`readOnly` または `eventName` フィルターを使用する場合は、必要なオペレーションと一致することを確認してください。
:::

:::

### Amazon Bedrock AgentCore データイベント {#amazon-bedrock-agentcore-data-events}

[Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/) は、AI エージェントの実行、セキュリティ保護、接続のためのマネージドインフラストラクチャを提供します — ホスティングされたランタイム、ビルトインツール（コードインタープリター、ブラウザ）、アイデンティティおよび認証情報管理、API ゲートウェイ、永続メモリを含みます。これらの各コンポーネントは、CloudTrail がデータイベントとしてキャプチャできるデータプレーンアクティビティを生成し、エージェントがコードを実行する方法、ウェブをブラウズする方法、サードパーティサービスに認証する方法、ゲートウェイを通じてユーザーとインタラクションする方法の可視性を提供します。

AgentCore データイベントは、エージェントの動作に関するランタイムの可視性を提供します。これには、コード実行、ツール使用、メモリオペレーション — エージェントが呼び出しているツール、取得している認証情報、トラフィックを受信しているゲートウェイ、認識されていない呼び出し元がエージェントインフラストラクチャにアクセスしているかどうかが含まれます。

#### AI セキュリティにおける AgentCore データイベントの重要性

AgentCore コンポーネントは AI エージェントのオペレーションサーフェスを表します — エージェントが実際のアクションを実行するレイヤーです。Bedrock データイベント（上記でカバー）がエージェントに求められたこと（モデルの呼び出し、ナレッジベースからの取得）をキャプチャするのに対し、AgentCore データイベントはエージェントが実際に行ったことをキャプチャします。[エージェント型 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)は、エージェント型システムの 6 つの重要なセキュリティディメンションを定義しています — 以下の項目は、各 AgentCore 機能をそれが対処するマトリックスディメンションにマッピングしています：

- **コード実行** — エージェントは CodeInterpreter を通じてユーザー提供のコードを実行でき、ファイルへのアクセス、ネットワークコール、副作用を引き起こす可能性があります。これらの呼び出しをモニタリングすることで、意図しないコード実行や、意図されたスコープ外で動作するエージェントを検出します。*（エージェント型マトリックス：[ガードレール](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/) — サンドボックス化と分離メカニズム）*
- **ウェブブラウジング** — ブラウザツールを使用するエージェントは外部ウェブサイトをナビゲートし、機密性の高い URL へのアクセスや、データ転送が意図した境界内に留まっているかの確認が必要になる場合があります。ブラウザアクティビティをログに記録することで、エージェントがアクセスしたすべてのページの監査証跡を提供します。*（エージェント型マトリックス：[ガードレール](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/) — 動作モニタリング）*
- **認証情報アクセス** — エージェントは TokenVault に保存された OAuth2 トークン、API キー、ワークロードアイデンティティトークンを使用してサードパーティ API に認証します。予期しない認証情報アクセスパターンは、異常なエージェントアクティビティや権限エスカレーションを示す可能性があります。*（エージェント型マトリックス：[アイデンティティ](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/) — アイデンティティ委任と認証情報管理）*
- **ゲートウェイトラフィック** — AgentCore ゲートウェイは JWT ベースの認証を持つ MCP プロトコルを通じてエージェントを外部呼び出し元に公開します。ゲートウェイデータイベントは、認証失敗を含むすべてのインバウンドリクエストをキャプチャします — AWS 環境外からの意図しないアクセス試行を検出するための鍵です。*（エージェント型マトリックス：[スコープ](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/) — 明確な運用境界）*
- **エージェントランタイムアクティビティ** — Runtime と RuntimeEndpoint イベントは、エージェントのライフサイクルオペレーション、セッション管理、エンドポイント呼び出しを追跡します。ここでの異常なパターンは、通常のオペレーションウィンドウ外でエージェントが開始、停止、またはアクセスされていることを示します。*（エージェント型マトリックス：[オーケストレーション](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/) — エージェントとシステム間のインタラクション管理）*
- **メモリオペレーション** — 永続メモリを持つエージェントは、セッション間で会話コンテキストを保存および取得します。意図しないメモリアクセスにより、会話履歴の取得やエージェントコンテキストの変更が可能になる場合があります。メモリオペレーションをモニタリングすることで、アクセスが認可されたスコープ内に留まっていることを検証できます。*（エージェント型マトリックス：[データ](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/) — 永続メモリと状態のセキュリティ）*
- **エージェント評価** — Evaluator イベントは、エージェント出力の自動品質・安全性評価を追跡します。これをモニタリングすることで、評価パイプラインが意図したとおりに設定されていることを確認できます。*（エージェント型マトリックス：[監査とログ](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/) — アクションレベルのエージェントアクション追跡）*

#### AgentCore 用のアドバンストイベントセレクター {#advanced-event-selectors-for-agentcore}

CloudTrail トレイルで AgentCore データイベントをキャプチャするには、以下のアドバンストイベントセレクターを使用します。これらのセレクターは、セキュリティ機能に基づいて 4 つのグループに整理されています：ビルトインツール、アイデンティティと認証情報、ランタイムとゲートウェイ、メモリと評価。各セレクターは `resources.ARN` プレフィックスを使用してログをスコープします。AWS マネージドビルトインツール（`CodeInterpreter` と `Browser`）では、AWS 所有の ARN を使用するため `resources.ARN` フィルターが省略されています — `resources.type` フィルターのみで十分です。

:::warning
以下のセレクターは**サンプル**です。プレースホルダーを置き換えずに適用すると、イベントはキャプチャされません。`ACCOUNT_ID` と `REGION` をお客様の値に置き換えてください（上記の [Bedrock プレースホルダーテーブル](#advanced-event-selectors-for-bedrock)を参照）。AgentCore 固有のプレースホルダーは以下にリストされています。
:::

:::note[AgentCore プレースホルダーリファレンス]

| プレースホルダー | 置き換え先 | 確認場所 |
|---|---|---|
| `GATEWAY_ID` | AgentCore ゲートウェイ ID | AgentCore コンソールまたは `ListGateways` API |
| `RUNTIME_ID` | AgentCore ランタイム ID | `ListRuntimes` API |
| `DIRECTORY_ID` | Workload Identity ディレクトリ ID | AgentCore コンソール |
| `PROVIDER_NAME` | OAuth2 または APIKey 認証情報プロバイダー名 | AgentCore コンソール |
| `MEMORY_ID` | AgentCore メモリ ID | AgentCore コンソール |
| `EVALUATOR_ID` | AgentCore エバリュエーター ID | AgentCore コンソール |
| `CUSTOM_TOOL_ID` / `CUSTOM_BROWSER_ID` | カスタムツールまたはブラウザ設定 ID | AgentCore コンソール |

特定のタイプの**すべて**のリソースをログに記録するには、ARN プレフィックスからリソース ID を削除します（例：`gateway/GATEWAY_ID` → `gateway/`）— これによりイベントボリュームとコストが増加します。
:::

### CloudTrail Insights イベント {#cloudtrail-insights-events}

[CloudTrail Insights](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-insights-events-with-cloudtrail.html) は、アカウントのオペレーションベースラインを継続的に分析することで、異常な API アクティビティを特定するよう設計されています。正当な使用自体が高いコール量を伴う可能性がある AI ワークロードでは、Insights は、絶対的なコール量が単独では妥当に見える場合でも、確立されたノルムから逸脱する異常なスパイクを検出する方法を提供します。

#### Insight タイプ

| Insight タイプ | 検出目的 |
|-------------|-------------------|
| ApiCallRateInsight | ベースラインから逸脱する API コール量のスパイクを検出します。 |
| ApiErrorRateInsight | 異常なエラーレートパターンを検出します。AccessDenied または ThrottlingException エラーの急激な増加は、認証情報への繰り返しアクセス試行、繰り返しの意図しないアクセス試行、またはレート制限に達した自動エージェントを示す可能性があります。 |

#### 設定ガイダンス

[CloudTrail コンソール](https://console.aws.amazon.com/cloudtrail/)でトレイルに移動し、**編集**を選択して、**Insights** セクションで両方の Insights イベントタイプを有効にすることで、トレイルで Insights を有効にします。

トレイルでは、管理イベントとデータイベントの両方に対して Insights を有効にできます。イベントタイプ（管理イベント、データイベント、またはその両方）を選択し、次に Insights タイプ（API コールレート、API エラーレート、またはその両方）を選択します。**API コールレート** Insights を有効にするには、トレイルが**書き込み**管理イベントまたはデータイベントをログに記録している必要があり、**API エラーレート** Insights を有効にするには、**読み取り**または**書き込み**管理イベントまたはデータイベントをログに記録している必要があります。

CloudTrail Insights イベントは、標準イベントと同じ Amazon S3 バケットおよび CloudWatch Logs ロググループに `Insights` プレフィックスの下で配信されます。異常なアクティビティが検出された場合の自動応答をトリガーするために、Insights イベントに対して直接メトリクスフィルターとアラームを作成できます。CloudTrail は、有効化後 Insights イベントの配信を開始するまでに最大 36 時間かかる場合があります（その間に異常なアクティビティが検出された場合）。

### CloudTrail 管理イベント {#cloudtrail-management-events}

CloudTrail 管理イベントは、AWS 環境でのコントロールプレーンオペレーションを記録するよう設計されています：リソースの作成と削除、設定の変更、権限の変更。AI ワークロードセキュリティでは、これらのイベントは予期しないアクセスパターンを表面化させます — ログの無効化、監査証跡のリダイレクト、AI サービスガードレールの弱体化など。

### Amazon S3 および Lambda データイベント {#amazon-s3-and-lambda-data-events}

AI ワークロードは Amazon S3 バケット（トレーニングデータ、モデルアーティファクト、CI/CD パイプラインアセット用）および Lambda 関数（AI 推論、データ前処理、エージェントオーケストレーション用）と頻繁にインタラクションします。これらのリソースタイプを[データイベント](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html)レベルでモニタリングすることで、管理イベントではキャプチャされないオブジェクトレベルおよび関数呼び出しレベルのアクティビティの可視性が得られます。

#### Amazon S3 ターゲットバケットとイベントタイプ

以下を含むバケットに対して Amazon S3 データイベントを有効にします：

- AI トレーニングデータセットとファインチューニングデータ
- モデルアーティファクトと設定ファイル
- CI/CD パイプラインアーティファクトとコードリポジトリ

モニタリングすべき主要な Amazon S3 オペレーション：

- **PutObject** — 不正な書き込みアクセスや不正データアクセスのためのデータステージングを検出します
- **GetObject** — トレーニングデータやモデルアーティファクトの一括ダウンロードを検出します
- **DeleteObject** — データ削除やログ変更アクティビティを検出します
- **CopyObject** — バケット間の意図しないデータ移動を検出します

#### Amazon S3 書き込みのみセレクター {#amazon-s3-write-only-selector}

以下のセレクターは、特定の名前の AI 関連バケットに対して書き込みオペレーションのみをログに記録することで、Amazon S3 データイベントボリュームを削減します：

:::warning[バケット名プレフィックスを実際のバケット名に置き換えてください]
以下のバケット名プレフィックス（`ai-training-data-`、`model-artifacts-`、`cicd-pipeline-`）は**サンプル**です。AI トレーニングデータ、モデルアーティファクト、パイプラインアセットを含む S3 バケットの実際の名前または命名プレフィックスに置き換えてください。バケット名は [S3 コンソール](https://console.aws.amazon.com/s3/)で確認するか、`aws s3 ls` を実行して確認できます。バケットが異なる命名規則を使用している場合は、`StartsWith` の値を適宜調整してください。
:::

:::info[この設定の動作]
Amazon S3 データイベントをフィルタリングして、名前が `ai-training-data-`、`model-artifacts-`、または `cicd-pipeline-` で始まるバケットに対する書き込みオペレーション（`readOnly = false`）のみをキャプチャします。これにより、不正な書き込み、削除、データステージングを検出しながら、大量の読み取りオペレーション（`GetObject` など）のログ記録を回避します。
:::

```json title="S3-AI-Sensitive-WriteOnly"
[
  {
    "Name": "S3-AI-Sensitive-WriteOnly",
    "FieldSelectors": [
      {
        "Field": "eventCategory",
        "Equals": ["Data"]
      },
      {
        "Field": "resources.type",
        "Equals": ["AWS::S3::Object"]
      },
      {
        "Field": "readOnly",
        "Equals": ["false"]
      },
      {
        "Field": "resources.ARN",
        "StartsWith": [
          "arn:aws:s3:::ai-training-data-",
          "arn:aws:s3:::model-artifacts-",
          "arn:aws:s3:::cicd-pipeline-"
        ]
      }
    ]
  }
]
```

#### Lambda AI パイプライン関数

以下の `InvokeFunction` コールをログに記録するために Lambda データイベントを有効にします：

- AI 推論パイプライン関数
- データ前処理およびフィーチャーエンジニアリングワークフロー
- Bedrock エージェントオーケストレーション関数

:::note
Lambda 呼び出しの予期しないスパイク、特に見慣れない IAM ロールからのものは、Lambda ベースの AI パイプライン関数への意図しないアクセスの早期指標です。
:::

#### Lambda 本番のみセレクター {#lambda-production-only-selector}

このセレクターは、開発およびテスト関数を除外して、本番 AI ワークロードにログを集中させます：

:::warning[関数名プレフィックスを実際の命名規則に置き換えてください]
以下の関数名プレフィックス（`prod-`、`ai-agent-`）は**サンプル**です。お客様の組織が本番 AI Lambda 関数に使用する実際の命名プレフィックスに置き換えてください。`ACCOUNT_ID` を AWS アカウント ID に、`REGION` をリージョンに置き換えてください。関数名は [Lambda コンソール](https://console.aws.amazon.com/lambda/)で確認するか、`aws lambda list-functions` を実行して確認できます。
:::

:::info[この設定の動作]
ARN が `prod-` または `ai-agent-` で始まる関数に対してのみ Lambda `Invoke` データイベントをログに記録します。`StartsWith` がすでにこれらの特定のプレフィックスにスコープされているため、開発およびテスト関数は定義上除外されます — CloudTrail は単一のセレクター内で同じフィールド（`resources.ARN`）に異なるオペレーターを持つ 2 つのフィールドセレクターを許可しません。`ACCOUNT_ID` とリージョンをお客様の値に置き換えてください。
:::

```json title="Lambda-AI-Production-Invocations"
[
  {
    "Name": "Lambda-AI-Production-Invocations",
    "FieldSelectors": [
      {
        "Field": "eventCategory",
        "Equals": ["Data"]
      },
      {
        "Field": "resources.type",
        "Equals": ["AWS::Lambda::Function"]
      },
      {
        "Field": "resources.ARN",
        "StartsWith": [
          "arn:aws:lambda:REGION:ACCOUNT_ID:function:prod-",
          "arn:aws:lambda:REGION:ACCOUNT_ID:function:ai-agent-"
        ]
      }
    ]
  }
]
```

### CloudTrail ネットワークアクティビティイベント {#cloudtrail-network-activity-events}

[CloudTrail ネットワークアクティビティイベント](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-network-events-with-cloudtrail.html)は、VPC エンドポイントオーナーがプライベート VPC から VPC エンドポイントを通じて行われた AWS API コールを記録できるよう設計されています。AI ワークロードでは、Bedrock 統合 VPC が予期しないアウトバウンドコールを行っているかどうか、または VPC エンドポイントアクセスコントロールが違反されているかどうかの可視性を提供します。*（[エージェント型 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)のスコープディメンションを実装します — 明確な運用境界の強制と、意図されたネットワーク境界外で動作するエージェントの検出。）*

#### AI ワークロード VPC エンドポイント

CloudTrail ネットワークアクティビティイベントは、Amazon Bedrock（`bedrock.amazonaws.com`）、Amazon S3（`s3.amazonaws.com`）、AWS Lambda（`lambda.amazonaws.com`）をイベントソースとしてサポートしています。各エンドポイントを通じてルーティングされた API コール（許可されたアクセスと拒否されたアクセスの両方）をキャプチャするために、VPC エンドポイントでこれらのイベントを有効にします。AI ワークロードでは、VPC 内で動作する Bedrock エージェントが VPC エンドポイントを通じてダウンストリームサービス — ナレッジベースデータソース用の Amazon S3、アクショングループハンドラー用の Lambda — にアクセスするため、これは特に重要です。VPC エンドポイントレベルでのアクセス拒否は、エンドポイントポリシーの設定ミスまたは、プライベートネットワーク内から AI リソースに到達しようとする不正なワークロードを示します。

有効にすることを検討すべき追加のイベントソース：

| イベントソース | モニタリング目的 |
|-------------|-------------------|
| bedrock.amazonaws.com | AI モデルアクセスをモニタリングし、VPC エンドポイントを通じた不正な呼び出しを検出します。 |
| s3.amazonaws.com | VPC エンドポイントを通じたトレーニングデータバケットへの不正な Amazon S3 アクセスを検出します。 |
| kms.amazonaws.com | AI モデル暗号化オペレーションの暗号化キーアクセスパターンをモニタリングします。 |
| lambda.amazonaws.com | AI パイプライン関数からの VPC エンドポイントを通じた Lambda 呼び出しを追跡します。 |
| sagemaker.amazonaws.com | AI ワークロード環境での SageMaker エンドポイントアクティビティを追跡します。 |

#### ネットワークアクティビティイベントのアドバンストイベントセレクターフィールド {#advanced-event-selector-fields-for-network-activity-events}

初期デプロイでは、すべての AI 関連 VPC エンドポイント間で `VpceAccessDenied` エラーをキャプチャすることに集中して、最小限の追加データボリュームで [VPC エンドポイントポリシー](https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints-access.html)の違反を検出します。以下のセレクターは Bedrock、Amazon S3、Lambda — AI エージェントが VPC エンドポイントを通じて最も一般的にアクセスする 3 つのサービスをカバーしています。

:::info[この設定の動作]
Bedrock、Amazon S3、Lambda が `VpceAccessDenied` エラーを返したネットワークアクティビティイベントをログに記録します。これは、VPC 内からのトラフィックが VPC エンドポイントポリシーによってブロックされたことを示します。すべての成功したネットワークアクティビティをログに記録するボリュームなしに、AI ワークロードサーフェス全体のアクセス拒否をキャプチャします。Amazon S3 の拒否は、トレーニングデータやモデルアーティファクトバケットに到達できないエージェントを検出します。Lambda の拒否は、アクショングループハンドラーや AI パイプライン関数を呼び出せないエージェントを検出します。
:::

### データイベント収集の最適化 {#optimizing-data-event-collection}

[アドバンストイベントセレクター](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html#creating-data-event-selectors-advanced)により、コストとログボリュームの両方を制御する精密なフィルタリングが可能になります。以下の戦略は、各主要リソースタイプをセキュリティ上関心のあるイベントのみに絞り込む方法を示しています。

#### Bedrock：本番リソースへの絞り込み

[上記のアドバンストイベントセレクター](#advanced-event-selectors-for-bedrock)は、すでに Bedrock データイベントを ARN によって特定のリソースにスコープしています。ボリュームをさらに削減するには、ARN プレフィックスを本番のエージェントとナレッジベースのみに絞り込み、非本番または実験的なリソースを除外します：

:::warning[リソース ID を実際の本番リソース識別子に置き換えてください]
以下のリソース ID（`PROD_AGENT_ID`、`PROD_KB_ID`）は**サンプル**です。本番環境の実際のエージェントおよびナレッジベース ID に置き換えてください。これらの ID は [Bedrock コンソール](https://console.aws.amazon.com/bedrock/)の**エージェント**と**ナレッジベース**で確認するか、`aws bedrock list-agents` および `aws bedrock list-knowledge-bases` を実行して確認できます。
:::

:::info[この設定の動作]
Bedrock データイベントログを、ARN が特定のリソース ID プレフィックスに一致するエージェントエイリアスとナレッジベースのみに制限します。本番で使用される正確なエージェントとナレッジベース ID を特定し、それ以外のすべてを除外したい場合に使用します。`ACCOUNT_ID` とリソース ID をお客様の値に置き換えてください。
:::

```json title="Bedrock-Production-Agents-Only"
[
  {
    "Name": "Bedrock-Production-Agents-Only",
    "FieldSelectors": [
      {
        "Field": "eventCategory",
        "Equals": ["Data"]
      },
      {
        "Field": "resources.type",
        "Equals": ["AWS::Bedrock::AgentAlias"]
      },
      {
        "Field": "resources.ARN",
        "StartsWith": [
          "arn:aws:bedrock:REGION:ACCOUNT_ID:agent-alias/PROD_AGENT_ID"
        ]
      }
    ]
  },
  {
    "Name": "Bedrock-Production-KnowledgeBases-Only",
    "FieldSelectors": [
      {
        "Field": "eventCategory",
        "Equals": ["Data"]
      },
      {
        "Field": "resources.type",
        "Equals": ["AWS::Bedrock::KnowledgeBase"]
      },
      {
        "Field": "resources.ARN",
        "StartsWith": [
          "arn:aws:bedrock:REGION:ACCOUNT_ID:knowledge-base/PROD_KB_ID"
        ]
      }
    ]
  }
]
```

#### Amazon S3：AI バケットへの書き込みのみ

AI 固有のバケットに対する書き込みオペレーションのみをログに記録することで、Amazon S3 データイベントボリュームを削減します。不正なデータ転送の検出を優先する場合は、高価値のバケットに対して後から読み取りオペレーションを追加できます。

> 完全な Amazon S3 書き込みのみアドバンストイベントセレクター JSON については、[セクション 6.2](#amazon-s3-write-only-selector) を参照してください。

#### インラインエージェント：IAM アイデンティティによるフィルター {#inline-agent-filter-by-iam-identity}

`AWS::Bedrock::InlineAgent` セレクターは、インラインエージェントに永続的なリソース ARN がないため、`resources.ARN` フィルタリングをサポートしません。追加のフィルタリングなしでは、このセレクターはアカウント全体のすべての `InvokeInlineAgent` コールをキャプチャし、大量のデータイベントボリュームとコストを生成する可能性があります。[`userIdentity.arn`](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-user-identity.html) フィールドを使用して、ログを特定の IAM ロール — 例えば本番の Bedrock 実行ロール — にスコープし、大量のインラインエージェントコールを生成する開発または自動サービスロールを除外します。

:::warning[ロール名を実際の IAM ロール名に置き換えてください]
以下のロール名（`BEDROCK_EXECUTION_ROLE_NAME`、`dev-`、`test-`）は**サンプル**です。`ACCOUNT_ID` を AWS アカウント ID に、`BEDROCK_EXECUTION_ROLE_NAME` をアプリケーションが `InvokeInlineAgent` を呼び出すために使用する実際の IAM ロール名に置き換えてください。ロール名は [IAM コンソール](https://console.aws.amazon.com/iam/)の**ロール**で確認するか、Bedrock エージェントに設定された実行ロールを確認できます。「開発ロールの除外」タブでは、`dev-` と `test-` をお客様の組織が非本番ロールに使用する実際の命名プレフィックスに置き換えてください。
:::

:::info[この設定の動作]
InlineAgent データイベントログを、特定の ARN プレフィックスに一致する IAM ロールによる呼び出しのみに制限します。`eventName` フィルターは `InvokeInlineAgent` コールのみのキャプチャに制限し、`userIdentity.arn` フィルターは本番ロールにスコープします。`ACCOUNT_ID` を AWS アカウント ID に、`BEDROCK_EXECUTION_ROLE_NAME` をアプリケーションが `InvokeInlineAgent` を呼び出すために使用する実際の IAM ロール名に置き換えてください。
:::

#### Lambda：本番関数のみ

`StartsWith` オペレーターを本番関数プレフィックス（`prod-`、`ai-agent-`）のみにスコープすることで、データイベントログを本番 AI ワークロードに集中させます。開発およびテスト関数は、プレフィックスが一致しないため、定義上除外されます。

> 完全な Lambda 本番のみアドバンストイベントセレクター JSON については、[セクション 6.4](#lambda-production-only-selector) を参照してください。

#### CloudTrail ネットワークアクティビティイベント：VpceAccessDenied のみ

ネットワークアクティビティイベントでは、Bedrock、Amazon S3、Lambda VPC エンドポイント間のアクセス拒否のみをログに記録することで、すべてのネットワークアクティビティをログに記録する場合と比較してボリュームを削減しながら、主要なセキュリティイベントをキャプチャします。

> 完全な Bedrock、Amazon S3、Lambda VpceAccessDenied ネットワークアクティビティイベントセレクター JSON については、[ネットワークアクティビティイベントのアドバンストイベントセレクターフィールド](#advanced-event-selector-fields-for-network-activity-events)を参照してください。

#### AgentCore：セキュリティ優先度によるフェーズド有効化

AgentCore データイベントは 14 のリソースタイプにまたがります。セキュリティ優先度に基づいてフェーズごとに有効にします：

1. **フェーズ 1（最高優先度）：** ゲートウェイ（`AWS::BedrockAgentCore::Gateway`）と認証情報アクセス（`TokenVault`、`OAuth2CredentialProvider`、`APIKeyCredentialProvider`）— 外部アクセスと認証情報取得をキャプチャし、最もセキュリティに敏感な 2 つのサーフェスです。
2. **フェーズ 2：** Runtime と RuntimeEndpoint — エージェントのライフサイクルとセッション管理をキャプチャします。
3. **フェーズ 3：** ビルトインツール（`CodeInterpreter`、`Browser` およびそのカスタムバリアント）— 実世界でのエージェントアクションをキャプチャします。
4. **フェーズ 4：** Memory、WorkloadIdentity、WorkloadIdentityDirectory、Evaluator — エージェントの状態とアイデンティティ管理をキャプチャします。

ゲートウェイデータイベントを特定のゲートウェイに絞り込むには、広い `gateway/` プレフィックスを特定のゲートウェイ ID に置き換えます：

```json
{
  "Field": "resources.ARN",
  "StartsWith": ["arn:aws:bedrock-agentcore:REGION:ACCOUNT_ID:gateway/PROD_GATEWAY_ID"]
}
```

同様に、ランタイムデータイベントを特定のエージェントランタイムに絞り込むには：

```json
{
  "Field": "resources.ARN",
  "StartsWith": ["arn:aws:bedrock-agentcore:REGION:ACCOUNT_ID:runtime/PROD_RUNTIME_ID"]
}
```

#### 組織レベルトレイルの CloudTrail アドバンストイベントセレクター

複数のアカウントをカバーする AWS Organizations トレイルでは、すべての AI ワークロードセレクターを単一のトレイル設定に統合します。これにより、Bedrock データイベント、AgentCore データイベント、S3 書き込みのみフィルタリング、Lambda 本番関数ログ、Bedrock ネットワークアクティビティのアクセス拒否検出を 1 つのトレイルに組み合わせた完全なアドバンストイベントセレクターセットが定義されます。

:::warning[適用前にすべてのプレースホルダー値を置き換えてください]
以下のセレクターは、すべてのサービスセレクターを単一の組織トレイルに統合した**サンプル**です。適用前にすべてのプレースホルダーを実際のリソース識別子に置き換える必要があります。

完全なプレースホルダーリファレンステーブルについては、上記の [Bedrock](#advanced-event-selectors-for-bedrock) と [AgentCore](#advanced-event-selectors-for-agentcore) セクションを参照してください。複数のアカウントにまたがる組織トレイルでは、異なる `ACCOUNT_ID` 値でセレクターを複製するか、各メンバーアカウントにスコープされたより広い ARN プレフィックスを使用する必要がある場合があります。
:::

### AI ワークロードのセキュリティ分析 {#security-analytics}

前のセクションでは CloudTrail がキャプチャする内容を設定しました — イベントセレクター、リソースタイプ、CloudWatch Logs への配信。このセクションでは、有効化から検出に移行します：以下のクエリは、意図しないアクセス試行やガードレール変更からエージェント認証情報アクセスやゲートウェイ認証失敗まで、それらのイベントに埋もれたセキュリティシグナルを表面化させます。

CloudWatch Logs Insights は [OpenSearch SQL 構文](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CWL_AnalyzeLogData_SQL.html)をサポートしており、ロググループ間の複雑な JOIN、クロスサービス相関のためのサブクエリ、時間ベースおよび集約分析のための豊富な SQL 関数セットが可能です。以下のすべてのクエリは AI ワークロードのユースケースに特化してスコープされています。クエリは管理イベント、データイベント（エージェント呼び出し、ナレッジベース取得、フロー呼び出し、AgentCore ゲートウェイトラフィック、ビルトインツール使用、認証情報アクセス、メモリオペレーション）、ネットワークアクティビティイベント（VPC エンドポイント拒否）、エージェントからリソースへのアクセスパターンのクロスサービス相関をカバーしています。

:::note[すべてのクエリでロググループ名を置き換えてください]
すべてのクエリはプレースホルダーとして `YOUR_CLOUDTRAIL_LOG_GROUP` を使用しています。CloudTrail トレイルがイベントを配信する CloudWatch Logs ロググループの名前に置き換えてください（例：`aws-cloudtrail-logs/management-events`）。これは CloudTrail コンソールのトレイルの **CloudWatch Logs** 設定で確認できます。パイプライン横断クエリでは `bedrock-model-invocation-logging` と `aws/spans` も参照しています — ロググループが異なる名前を使用している場合はそれらも置き換えてください。
:::

:::warning[重要]
CloudWatch Logs Insights で OpenSearch SQL 構文を使用する場合、特殊文字を含むフィールドはバッククォートで囲みます。例：`` `userIdentity.arn` ``、`` `responseElements.ConsoleLogin` ``。ダッシュボードでこれらのクエリウィジェットを作成する場合は、クエリ言語を **SQL** に設定してください。
:::

```sql title="クエリ 1：不正な Bedrock アクセスの検出"
GROUP BY `userIdentity.arn`, eventName, errorCode, errorMessage, sourceIPAddress
ORDER BY attempt_count DESC
```

**クエリ 2：IAM アイデンティティ別の Bedrock エージェント呼び出しのモニタリング**

<details>
<summary>Bedrock エージェントおよびインラインエージェントの呼び出しをトリガーしている IAM アイデンティティを追跡します</summary>

Bedrock エージェントおよびインラインエージェントの呼び出しをトリガーしている IAM アイデンティティを追跡します。エージェントは 1 回の呼び出しで複数のダウンストリーム API コールをチェーンできるため、高いアクセスのスコープを持ちます。見慣れないアイデンティティやボリュームスパイクは、認識されていない呼び出し元によってエージェントがトリガーされている可能性があることを示します。このクエリは `AWS::Bedrock::AgentAlias` と `AWS::Bedrock::InlineAgent` のアドバンストイベントセレクターによってキャプチャされたデータイベントを対象としています。

```sql title="クエリ 2：IAM アイデンティティ別の Bedrock エージェント呼び出し"
SELECT `userIdentity.arn` AS iam_identity,
       eventName,
       sourceIPAddress,
       awsRegion,
       COUNT(*) AS agent_invocation_count
FROM `YOUR_CLOUDTRAIL_LOG_GROUP`
WHERE eventSource = 'bedrock.amazonaws.com'
  AND eventName IN ('InvokeAgent', 'InvokeInlineAgent')
GROUP BY `userIdentity.arn`, eventName, sourceIPAddress, awsRegion
ORDER BY agent_invocation_count DESC
```

</details>

**クエリ 3：IAM アイデンティティ別のナレッジベース取得アクティビティのモニタリング**

<details>
<summary>Bedrock ナレッジベースに対する Retrieve および RetrieveAndGenerate コールを行っている IAM アイデンティティをランク付けします</summary>

Bedrock ナレッジベースに対する `Retrieve` および `RetrieveAndGenerate` コールを行っている IAM アイデンティティをランク付けします。ナレッジベースにはお客様の組織の独自データが含まれています — 見慣れないアイデンティティや予期しないボリュームスパイクは、異常なデータアクセスを示す可能性があります。このクエリは `AWS::Bedrock::KnowledgeBase` のアドバンストイベントセレクターによってキャプチャされたデータイベントを対象としています。

```sql title="クエリ 3：ナレッジベース取得アクティビティ"
SELECT `userIdentity.arn` AS iam_identity,
       eventName,
       sourceIPAddress,
       COUNT(*) AS retrieval_count
FROM `YOUR_CLOUDTRAIL_LOG_GROUP`
WHERE eventSource = 'bedrock.amazonaws.com'
  AND eventName IN ('Retrieve', 'RetrieveAndGenerate')
GROUP BY `userIdentity.arn`, eventName, sourceIPAddress
ORDER BY retrieval_count DESC
```

</details>

**クエリ 4：エージェントのクロスサービスアクセス拒否の検出**

<details>
<summary>Amazon S3、Lambda、KMS、Secrets Manager、SageMaker などのダウンストリームサービスへのアクセスが拒否された引き受けたロールを表面化させます</summary>

引き受けたロール — 通常は Bedrock エージェント実行ロール — が Amazon S3、Lambda、KMS、Secrets Manager、SageMaker に到達しようとした際にアクセスを拒否された場合を表面化させます。これはエージェントからリソースへのアクセス制御例外を検出するための重要なクエリです。単一のロールからの高いカウントは、設定ミスのエージェント権限境界またはエージェントが意図されたスコープ外のリソースにアクセスしていることを示します。*（[エージェント型 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)のアイデンティティディメンション — 混乱した代理問題の検出 — およびスコープディメンション — 運用境界の強制を実装します。また、[生成 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/generative-ai-scoping-matrix/)のコントロールディメンション — 最小権限アクセスの強制も実装します。）*

```sql title="クエリ 4：エージェントのクロスサービスアクセス拒否"
SELECT `userIdentity.arn` AS iam_identity,
       eventSource,
       eventName,
       errorCode,
       errorMessage,
       sourceIPAddress,
       COUNT(*) AS denied_count
FROM `YOUR_CLOUDTRAIL_LOG_GROUP`
WHERE errorCode IN ('AccessDenied', 'UnauthorizedOperation')
  AND `userIdentity.type` = 'AssumedRole'
  AND eventSource IN (
    's3.amazonaws.com',
    'lambda.amazonaws.com',
    'kms.amazonaws.com',
    'secretsmanager.amazonaws.com',
    'sagemaker.amazonaws.com'
  )
GROUP BY `userIdentity.arn`, eventSource, eventName, errorCode, errorMessage, sourceIPAddress
ORDER BY denied_count DESC
```

</details>

**クエリ 6：予期しないソース IP からの Bedrock コールの検出**

<details>
<summary>Bedrock および AgentCore コールを行っているすべてのユニークなソース IP アドレスをリストします</summary>

Bedrock および AgentCore コールを行っているすべてのユニークなソース IP アドレスをリストします — モデル呼び出し、エージェント呼び出し、ナレッジベース取得、フロー呼び出し、非同期呼び出し、ガードレール適用、AgentCore ゲートウェイ呼び出しを含みます。AI ワークロードが特定の CIDR 範囲（VPC NAT ゲートウェイ、企業ネットワーク）からのみ発信されるべき場合、見慣れない IP アドレスは認可されていることを確認するために調査する必要があります。

```sql title="クエリ 6：予期しないソース IP からの Bedrock コール"
SELECT sourceIPAddress,
       `userIdentity.arn` AS iam_identity,
       eventSource,
       eventName,
       COUNT(*) AS call_count
FROM `YOUR_CLOUDTRAIL_LOG_GROUP`
WHERE eventSource IN ('bedrock.amazonaws.com', 'bedrock-agentcore.amazonaws.com')
  AND eventName IN ('InvokeModel', 'InvokeModelWithResponseStream',
                    'Converse', 'ConverseStream',
                    'InvokeAgent', 'InvokeInlineAgent',
                    'Retrieve', 'RetrieveAndGenerate',
                    'InvokeFlow', 'ApplyGuardrail',
                    'InvokeModelWithBidirectionalStream',
                    'GetAsyncInvoke', 'StartAsyncInvoke',
                    'RenderPrompt', 'InvokeGateway')
GROUP BY sourceIPAddress, `userIdentity.arn`, eventSource, eventName
ORDER BY call_count DESC
```

</details>

**クエリ 23：Bedrock セッションアクティビティのモニタリング**

<details>
<summary>マルチターン Bedrock 会話のセッションレベル API アクティビティを追跡します</summary>

セッション作成、更新、取得を含む Bedrock 全体のすべてのセッションオペレーションを表面化させます。セッションはマルチターン会話間で状態を維持します — 見慣れないアイデンティティがセッションを作成またはアクセスしている場合、会話型 AI リソースの異常な使用を示す可能性があります。*（[エージェント型 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)のオーケストレーションディメンション — エージェントとシステム間のインタラクション管理とセッションフロー制御を実装します。）*


**クエリ 24：Bedrock フロー実行アクティビティのモニタリング**

### パイプライン横断の相関クエリ {#cross-pipeline-correlation-queries}

上記のクエリは CloudTrail 単独で動作します。以下のクエリは CloudTrail を Bedrock モデル呼び出しログおよび ADOT スパンと結合して、単一のパイプラインでは回答できない質問に答えます。

:::info[前提条件]
これらのクエリには 3 つのパイプラインすべてが有効になっている必要があります：

- Bedrock および AgentCore の管理イベントとデータイベントで `YOUR_CLOUDTRAIL_LOG_GROUP` に配信される CloudTrail
- [Bedrock モデル呼び出しログ](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/model-invocations.html)が有効で、`bedrock-model-invocation-logging` に配信
- [エージェントテレメトリ（ADOT SDK）](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/AgentCore-GettingStarted.html)が `aws/spans` に流入
- ダッシュボードでこれらのウィジェットを作成する場合、クエリ言語を **SQL** に設定（すべての相関クエリは OpenSearch SQL を使用）
:::

#### 相関キー

| 結合 | キーフィールド | 注意事項 |
| --- | --- | --- |
| CloudTrail ↔ モデル呼び出しログ | `requestID`（CT）= `requestId`（呼び出しログ） | 同じ Bedrock API コールの異なるビュー |
| CloudTrail ↔ ADOT スパン | `requestID`（CT）= `attributes.aws.request_id`（スパン） | 両方が同じ Bedrock リクエストを参照 |
| ADOT スパン ↔ モデル呼び出しログ | `attributes.aws.request_id`（スパン）= `requestId`（呼び出しログ） | 同じモデルコール、スパンにはレイテンシが含まれ、MIL にはコンテンツが含まれます |
| エージェントセッション間 | `attributes.session.id`（スパン） | エージェントフレームワークがセッションを設定。CloudTrail や MIL にはありません |

:::tip[各クエリを展開]
以下の任意のクエリタイトルをクリックして展開し、完全な説明、メタデータ、SQL ステートメントを表示できます。
:::

**クエリ 18：誰が何を尋ね、モデルは何と答えたか？**

<details>
<summary>CloudTrail の呼び出し元アイデンティティと Bedrock モデル呼び出しログのプロンプトおよびレスポンスコンテンツを結合します</summary>

- **目的：** CloudTrail（呼び出し元アイデンティティ、ソース IP）と Bedrock モデル呼び出しログ（プロンプトとレスポンスコンテンツ）を `requestId` で結合します。「誰がモデルに何を尋ね、モデルは何と答えたか？」に回答するために頻繁に使用されるクエリです — セキュリティ監査、コンプライアンスレビュー、ハルシネーション調査の基盤。例：顧客が不快なモデルレスポンスを報告した場合、このクエリで呼び出し元の IAM ロール、ソース IP、送信された正確なプロンプト、使用された推論パラメータ、レスポンスが 1 行で得られます。*（[生成 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/generative-ai-scoping-matrix/)のガバナンスとコンプライアンスディメンション — データ主権とコンプライアンスレビュープロセスをサポートする監査証跡 — および[エージェント型 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)の監査とログディメンション — アイデンティティコンテキスト付きのアクションレベルのアクション追跡を実装します。）*
- **ソース：** `YOUR_CLOUDTRAIL_LOG_GROUP` + `bedrock-model-invocation-logging`
- **ビュー：** テーブル
- **クエリ言語：** OpenSearch SQL

```sql title="クエリ 18：誰が何を尋ね、モデルは何と答えたか？"
SELECT
  ct.eventTime AS timestamp,
  ct.`userIdentity.arn` AS caller,
  ct.sourceIPAddress AS sourceIP,
  ct.eventName AS api,
  ct.`userIdentity.inScopeOf.credentialsIssuedTo` AS lambdaFunction,
  ct.requestID AS requestId,
  ct.`additionalEventData.inputTokens` AS inputTokens,
  ct.`additionalEventData.outputTokens` AS outputTokens,
  inv.`input.inputBodyJson.messages.0.content.0.text` AS prompt,
  inv.`input.inputBodyJson.inferenceConfig.temperature` AS temperature,
  inv.`input.inputBodyJson.inferenceConfig.maxTokens` AS maxTokens,
  inv.`output.outputBodyJson.stopReason` AS stopReason,
  inv.`output.outputBodyJson.output.message.content.0.text` AS response,
  inv.`output.outputBodyJson.usage.cacheReadInputTokens` AS cacheReadTokens,
  inv.`output.outputBodyJson.usage.cacheCreationInputTokens` AS cacheWriteTokens,
  inv.inferenceRegion
FROM `YOUR_CLOUDTRAIL_LOG_GROUP` AS ct
LEFT OUTER JOIN `bedrock-model-invocation-logging` AS inv
  ON ct.requestID = inv.requestId
WHERE ct.eventSource = 'bedrock.amazonaws.com'
  AND ct.eventName IN ('InvokeModel', 'InvokeModelWithResponseStream',
                        'Converse', 'ConverseStream')
ORDER BY ct.eventTime DESC
LIMIT 20
```

</details>

**クエリ 19：呼び出し元アイデンティティ付きのエージェントセッションパフォーマンス**

<details>
<summary>ADOT スパンと CloudTrail を結合して、エージェントセッションパフォーマンスを呼び出し元アイデンティティにリンクします</summary>

- **目的：** ADOT スパン（session.id、レイテンシ、トークン数）と CloudTrail（呼び出し元 IAM ロール、ソース IP）を `requestId` で結合します。「このエージェントセッションの背後にどの IAM アイデンティティがあり、パフォーマンスはどうか？」に回答します。例：ADOT ダッシュボードで p95 レイテンシが 12 秒の遅いエージェントセッションが表示された場合、このクエリで高コストなモデルを呼び出している特定の Lambda 関数または AgentCore ランタイムであることが判明します — 呼び出し元のモデル選択をチューニングできるようになります。
- **ソース：** `aws/spans` + `YOUR_CLOUDTRAIL_LOG_GROUP`
- **ビュー：** テーブル
- **クエリ言語：** OpenSearch SQL

```sql title="クエリ 19：呼び出し元アイデンティティ付きのエージェントセッションパフォーマンス"
SELECT
  spans.`attributes.session.id` AS sessionId,
  spans.traceId,
  spans.`attributes.gen_ai.request.model` AS model,
  spans.durationNano / 1000000 AS latencyMs,
  spans.`attributes.gen_ai.usage.input_tokens` AS inputTokens,
  spans.`attributes.gen_ai.usage.output_tokens` AS outputTokens,
  ct.`userIdentity.arn` AS caller,
  ct.sourceIPAddress AS sourceIP,
  ct.`userIdentity.inScopeOf.issuerType` AS callerType,
  ct.`userIdentity.inScopeOf.credentialsIssuedTo` AS callerResource
FROM `aws/spans` AS spans
LEFT OUTER JOIN `YOUR_CLOUDTRAIL_LOG_GROUP` AS ct
  ON spans.`attributes.aws.request_id` = ct.requestID
WHERE spans.`resource.attributes.aws.service.type` = 'gen_ai_agent'
  AND spans.`attributes.gen_ai.system` = 'aws.bedrock'
ORDER BY spans.`attributes.session.id`, spans.startTimeUnixNano DESC
LIMIT 50
```

</details>

**クエリ 20：完全な 3 パイプライン結合 — セッション、コンテンツ、パフォーマンス**

<details>
<summary>requestId で 3 つのロググループすべてを結合し、単一のモデル呼び出しの統合ビューを提供します</summary>

- **目的：** `requestId` で 3 つのロググループすべてを結合して、エージェントセッション（ADOT）、モデルコールコンテンツ（モデル呼び出しログ）、呼び出し元アイデンティティ（CloudTrail）を含む単一の行を提供します。テレメトリスタック全体にわたる単一のモデル呼び出しの統合ビューです。すべてが必要な詳細なイベント調査に使用します — 誰が呼び出したか、何を尋ねたか、モデルは何と答えたか、どのくらい時間がかかったか、どのエージェントセッションに属しているか。
- **ソース：** `YOUR_CLOUDTRAIL_LOG_GROUP` + `bedrock-model-invocation-logging` + `aws/spans`
- **ビュー：** テーブル
- **クエリ言語：** OpenSearch SQL

```sql title="クエリ 20：完全な 3 パイプライン結合"
SELECT
  ct.eventTime AS timestamp,
  ct.`userIdentity.arn` AS caller,
  ct.sourceIPAddress AS sourceIP,
  spans.`attributes.session.id` AS sessionId,
  spans.traceId,
  spans.durationNano / 1000000 AS latencyMs,
  inv.modelId,
  inv.`input.inputBodyJson.inferenceConfig.temperature` AS temperature,
  inv.`input.inputBodyJson.messages.0.content.0.text` AS prompt,
  inv.`output.outputBodyJson.output.message.content.0.text` AS response,
  inv.`output.outputBodyJson.stopReason` AS stopReason,
  inv.`input.inputTokenCount` AS inputTokens,
  inv.`output.outputTokenCount` AS outputTokens
FROM `YOUR_CLOUDTRAIL_LOG_GROUP` AS ct
LEFT OUTER JOIN `bedrock-model-invocation-logging` AS inv
  ON ct.requestID = inv.requestId
LEFT OUTER JOIN `aws/spans` AS spans
  ON ct.requestID = spans.`attributes.aws.request_id`
WHERE ct.eventSource = 'bedrock.amazonaws.com'
  AND ct.eventName IN ('InvokeModel', 'Converse', 'ConverseStream')
ORDER BY ct.eventTime DESC
LIMIT 20
```

</details>

**クエリ 21：ガードレール変更とダウンストリームモデルコンテンツの相関**

<details>
<summary>CloudTrail でガードレール変更を見つけ、変更後のモデルレスポンスと相関させます</summary>

- **目的：** CloudTrail で `UpdateGuardrail` または `DeleteGuardrail` イベントを見つけ、変更後のウィンドウ内のモデルレスポンスと相関させます。ガードレール変更が未検証またはポリシー外のモデル出力に先行したかどうかを検出します。例：`UpdateGuardrail` でセキュリティアラートがトリガーされた場合、このクエリは弱体化されたガードレール下で生成されたモデルレスポンスをすぐにレビュー用に表示します。*（[エージェント型 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)のガードレールディメンション — 動的な動作モニタリング — および[生成 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/generative-ai-scoping-matrix/)のリスク管理ディメンション — ガードレール変更とそのダウンストリームインパクトの検出を実装します。）*
- **ソース：** `YOUR_CLOUDTRAIL_LOG_GROUP` + `bedrock-model-invocation-logging`
- **ビュー：** テーブル
- **クエリ言語：** OpenSearch SQL

```sql title="クエリ 21：ガードレール変更とモデルコンテンツの相関"
SELECT
  ct.eventTime AS guardrailChangeTime,
  ct.`userIdentity.arn` AS whoChangedGuardrail,
  ct.eventName AS changeType,
  inv.timestamp AS modelCallTime,
  inv.`identity.arn` AS modelCaller,
  inv.modelId,
  inv.`output.outputBodyJson.stopReason` AS stopReason,
  inv.`output.outputBodyJson.output.message.content.0.text` AS response
FROM `YOUR_CLOUDTRAIL_LOG_GROUP` AS ct
LEFT OUTER JOIN `bedrock-model-invocation-logging` AS inv
  ON inv.timestamp >= ct.eventTime
WHERE ct.eventSource = 'bedrock.amazonaws.com'
  AND ct.eventName IN ('UpdateGuardrail', 'DeleteGuardrail', 'DeleteGuardrailVersion')
ORDER BY ct.eventTime DESC
LIMIT 50
```

</details>

**クエリ 22：クロスサービスアクセス拒否付きのエージェントセッション**

<details>
<summary>ADOT エージェントセッションと同じ引き受けたロールからの CloudTrail AccessDenied イベントを相関させます</summary>

- **目的：** ADOT エージェントセッションと同じ引き受けたロールからの CloudTrail AccessDenied イベントを相関させます。「どのエージェントセッションがダウンストリームサービスで権限エラーをトリガーしたか？」に回答します。例：エージェントがツールから 5xx レスポンスを返す場合、このクエリで根本原因がツール自体ではなくダウンストリームサービスでの IAM 拒否であるかどうかが判明します — 多くの場合、設定ミスのエージェント権限境界です。
- **ソース：** `aws/spans` + `YOUR_CLOUDTRAIL_LOG_GROUP`
- **ビュー：** テーブル
- **クエリ言語：** OpenSearch SQL

```sql title="クエリ 22：クロスサービスアクセス拒否付きのエージェントセッション"
SELECT
  spans.`attributes.session.id` AS sessionId,
  spans.`resource.attributes.service.name` AS agentService,
  ct.eventTime AS denialTime,
  ct.`userIdentity.arn` AS agentRole,
  ct.eventSource AS blockedService,
  ct.eventName AS blockedAction,
  ct.errorCode,
  ct.errorMessage
FROM `aws/spans` AS spans
LEFT OUTER JOIN `YOUR_CLOUDTRAIL_LOG_GROUP` AS ct
  ON ct.`userIdentity.arn` = spans.`attributes.aws.local.service`
WHERE spans.`resource.attributes.aws.service.type` = 'gen_ai_agent'
  AND ct.errorCode IN ('AccessDenied', 'UnauthorizedOperation')
  AND ct.`userIdentity.type` = 'AssumedRole'
  AND ct.eventSource IN (
    's3.amazonaws.com', 'lambda.amazonaws.com',
    'kms.amazonaws.com', 'secretsmanager.amazonaws.com',
    'sagemaker.amazonaws.com'
  )
ORDER BY ct.eventTime DESC
LIMIT 50
```

</details>

:::tip[パフォーマンスに関する注意]
CloudWatch Logs Insights SQL でのロググループ横断の JOIN は、大規模なデータセットでは低速になる可能性があります。ダッシュボードウィジェットとして長い時間範囲でスケジュールする前に、狭い時間ウィンドウ（直近 15 分、直近 1 時間）でテストしてください。継続的な相関の場合は、3 つのロググループすべてを単一の送信先（S3、OpenSearch）にエクスポートし、そこで結合を実行することを検討してください。
:::

### メトリクスフィルター {#metric-filters}

[メトリクスフィルター](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html)は、CloudTrail ログイベントから値を抽出してカスタム CloudWatch メトリクスを作成するよう設計されており、継続的なクエリなしでニアリアルタイムのアラートを可能にします。[フィルターパターン構文](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/FilterAndPatternSyntax.html)は JSON プロパティセレクターを使用して CloudTrail イベントレコードの特定のフィールドに一致させます。以下のフィルターは AI ワークロードセキュリティイベントに特化してスコープされています — Bedrock リソースへの不正アクセス、エージェントアクティビティの異常、ガードレールの変更、AI インフラストラクチャの設定変更を検出します。

<Tabs>
  <TabItem value="bedrock-access" label="Bedrock アクセスとアクティビティ" default>

**メトリクスフィルター 1：Bedrock サービスへの不正アクセス**

<details>
<summary>Bedrock API に対する AccessDenied および UnauthorizedOperation エラーをキャプチャします</summary>

単一のアイデンティティからの Bedrock 拒否コールの急激な増加は、繰り返しの意図しないアクセス試行、またはエージェントが認可されたスコープ外のモデルやナレッジベースへのアクセスを試みていることを示すことが多いです。

**フィルターパターン：**

```
{ ($.eventSource = "bedrock.amazonaws.com") && (($.errorCode = "AccessDenied") || ($.errorCode = "UnauthorizedOperation")) }
```

- **メトリクス名前空間：** `AIWorkloadMetrics`
- **メトリクス名：** `BedrockUnauthorizedAccess`

</details>

<details>
<summary>Bedrock エージェントとインラインエージェントの呼び出しをカウントします</summary>

エージェントは単一の呼び出し内で複数のサービスにわたる複数の API コールをチェーンできるため、インパクトの大きいサーフェスです。このメトリクスを追跡して、認識されていない呼び出し元によってトリガーされている可能性のある予期しないエージェントアクティビティやボリュームスパイクを検出します。

### Contributor Insights ルール {#contributor-insights-rules}

[CloudWatch Contributor Insights](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/ContributorInsights.html) は、CloudWatch Logs ロググループ内のアクティビティパターンに影響を与えるトップコントリビューターをニアリアルタイムで分析して表面化させるよう設計されています。CloudTrail ロググループに適用すると、Contributor Insights ルールは手動でのクエリ実行なしに、AI ワークロード全体のアクティビティを駆動するトップ IAM アイデンティティ、リソース、ソース IP を継続的に特定します。以下のルールは、ガイドがキャプチャするすべてのイベントカテゴリをカバーしています：管理イベント、データイベント、ネットワークアクティビティイベント、セキュリティ設定変更。

:::warning[重要]
Contributor Insights ルールは CloudWatch Logs **Standard** ロググラスのロググループにのみ適用できます。CloudTrail 配信ロググループが Standard クラスに設定されていることを確認してください。
:::

### CloudTrail データイベント集約 {#cloudtrail-data-event-aggregation}

[イベント集約](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/aggregating-data-events.html)は、データイベントを 5 分間のサマリーに統合するよう設計されており、アクセス頻度、エラーレート、最も頻繁に使用される API アクションなどの主要なトレンドの可視性を提供します。これにより、セキュリティモニタリングとトレンド分析に必要な推奨インサイトを維持しながら、ダウンストリーム分析システムに送信されるデータボリュームを大幅に削減します。集約イベントは[集約イベントレコード](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-aggregated-events.html)で `eventCategory = Aggregated` および `eventType = AwsAggregatedEvent` フィールドを使用します。

#### 集約の有効化

[CloudTrail コンソール](https://console.aws.amazon.com/cloudtrail/)に移動してトレイルを選択します。**集約イベント**セクションで**編集**を選択し、以下の集約テンプレートを有効にします：

- **API アクティビティ** — 頻度、トップ呼び出し元、ソース IP 分布を含む、行われた API コールに基づくデータイベントの 5 分間サマリー
- **リソースアクセス** — 誰がどのリソースに何回アクセスしているかを示す、AWS リソースのアクティビティパターン
- **ユーザーアクション** — API コールを行っている IAM プリンシパルに基づくアクティビティパターン。行動異常の特定に有用

#### CloudTrail 集約イベントのクエリ

集約イベントは `eventCategory = 'Aggregated'` で CloudWatch Logs ロググループ内の標準イベントと並行して配信されます。以下の OpenSearch SQL クエリを使用して、集約された Bedrock API アクティビティサマリーを表面化させます：

```sql title="クエリ：集約された Bedrock API アクティビティ"
SELECT eventTime,
       eventSource,
       `summary.primaryDimension.dimension` AS primary_dimension,
       `timeWindow.windowStart` AS window_start,
       `timeWindow.windowEnd` AS window_end
FROM `YOUR_CLOUDTRAIL_LOG_GROUP`
WHERE eventCategory = 'Aggregated'
  AND eventSource = 'bedrock.amazonaws.com'
ORDER BY eventTime DESC
```

#### ダウンストリーム効率化のためのサブスクリプションフィルター

SIEM や Kinesis Data Firehose などのダウンストリームシステムに送信されるボリュームを削減するには、生のデータイベントの代わりに管理イベントと集約サマリーのみを転送する [CloudWatch Logs サブスクリプションフィルター](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/SubscriptionFilters.html)を作成します。これにより、5 分間の集約サマリーからの推奨セキュリティインサイトを維持しながら、ダウンストリームの取り込みボリュームを削減します。

**サブスクリプションフィルターパターン（管理 + 集約イベントのみ）：**

```
{ ($.eventCategory = "Management") || ($.eventCategory = "Aggregated") }
```

### まとめと次のステップ

このガイドでは、AWS 上の AI ワークロードのエンドツーエンドのモニタリングと監査アーキテクチャをカバーしました — 3 つのテレメトリパイプライン、各パイプラインの有効化、Bedrock および AgentCore データイベントの両方に対する CloudTrail 固有の検出（メトリクスフィルター、アラーム、Contributor Insights）、CloudTrail を Bedrock モデル呼び出しログおよび ADOT スパンと結合するパイプライン横断の相関クエリ、統合 CloudWatch ダッシュボード。各セクションは[実装の概要](#implementation-overview)のフェーズドロードマップに従って段階的に実装されるよう設計されています。

核となるアイデア：CloudTrail 単独では*誰が何をしたか*を示し、モデル呼び出しログは*モデルが何と言ったか*を示し、ADOT は*エージェントがどのように動作したか*を示します。AgentCore データイベントにより、CloudTrail は*エージェントが実際に何をしたか*も示すようになりました — どのツールを呼び出したか、どの認証情報にアクセスしたか、どのゲートウェイがトラフィックを受信したか、メモリに何を保存したか。価値は調査中にこれらのシグナルを結合することにあります — 単一のパイプラインではすべての質問に答えることはできません。

これらの機能を合わせることで、[生成 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/generative-ai-scoping-matrix/)および[エージェント型 AI セキュリティスコーピングマトリックス](https://aws.amazon.com/ai/security/agentic-ai-scoping-matrix/)で定義されたセキュリティディメンションの具体的な実装を提供します。

#### 次のステップ

1. **フェーズ 1 から開始します。** 3 つのテレメトリパイプラインすべてを有効にします。他の 2 つ（モデル呼び出しログ、ADOT）が相関クエリを可能にします。
2. **CloudTrail Bedrock データイベントを有効にします。** AI ワークロードの監査に不可欠なステップです。
3. **CloudTrail AgentCore データイベントを有効にします。** ゲートウェイと認証情報アクセス（グループ 2 と 3）から開始し、ベースラインボリュームを確立した後にビルトインツールとメモリ（グループ 1 と 4）に拡張します。
4. **ベースラインを検証します。** [セキュリティ分析](#security-analytics)のクエリ 2 と 4、および[セキュリティ分析](#security-analytics)の AgentCore タブのクエリ 12-14 を実行して、アラームしきい値を設定する前に通常の使用状況を確立します。
4. **レスポンスを自動化します。** CloudWatch アラームを [Amazon SNS](https://docs.aws.amazon.com/sns/latest/dg/welcome.html) トピック、[AWS Lambda](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html) 関数、または [Systems Manager ランブック](https://docs.aws.amazon.com/systems-manager/latest/userguide/automation-documents.html)に接続して、検出と修復のギャップを埋めます。
5. **GuardDuty と統合します。** [Amazon GuardDuty](https://docs.aws.amazon.com/guardduty/latest/ug/what-is-guardduty.html) は、ここでのカスタムモニタリングを補完するマネージド脅威検出を提供します。GuardDuty は、検出ルールを維持する必要なしに、既知の脅威パターンについて CloudTrail イベントを分析します。
6. **コストをレビューします。** データイベント、Insights 分析、ネットワークアクティビティイベントはすべて料金が発生します。[CloudTrail の料金ページ](https://aws.amazon.com/cloudtrail/pricing/)と[データイベント収集の最適化](#optimizing-data-event-collection)のボリューム削減戦略を使用してください。
